## 1. What the example gives us (and what it is not)

The example is an **image** app: it registers image directories, slices graphs, runs vision-model scans, compares two models per image and builds similarity histograms. Our frontend is a **text chat** app: chat, replay a conversation on two models, knowledge bases per agent, provider settings. The domains differ, so we use it as a **reference** for architecture and conventions, write all code fresh, and take only a few of its model designs as inspiration.

Conventions to keep (so both codebases feel the same):

- Layering: `api/routes_*.py` -> `controllers/*_controller.py` -> `services/*.py` -> `repositories/*.py` -> `db/connection.py` (SQLite). Pydantic models in `models/` hold both the domain objects and the request bodies.
- Raw `sqlite3`, wrapped in `asyncio.to_thread` in each repository; `sqlite3.Row` mapped to Pydantic models.
- Seeded by SQL plus a schema file. The example has **no migrations** and `./run.sh` wipes `app.db` on every run. **We differ**: the database persists, and schema changes are numbered migrations (section 5).
- JSON stored as `TEXT` columns named `*_json`; ids are strings (uuid4).
- Cookie session auth (`session_token`, httponly), PBKDF2 password hashing, Fernet-encrypted provider keys.
- `api/deps.py` `get_current_user` dependency; `Depends(get_settings)` everywhere so tests override settings.
- Tests: pytest + `TestClient`, a temp DB per test, and an **autouse stub at the LLM service seam** so tests never call a provider.
- Immutable rows plus link tables (scan sessions, label jobs) for forking a conversation. **We do not carry this over** (see section 5).

## 5a. Approach: reference only (no copying)

`example_backend/Multiverse_Replay` is a **read-only reference**. We write every file fresh in `backend/`, using the example only to see how the same problems were solved on the same stack. Why not copy or fork it: only about a fifth of its ~5,400 backend lines fit our app, and parts are entangled with things we do not want (an outbound bananalon.com call at startup, a `focusari/aurapacker` uv workspace dependency, `matplotlib`/`pillow`/`pydantic-ai`, the old static frontend mounted at `/`, tests that stub four image agents).

**Rules**

1. Do not copy files or paste blocks; read, then write our own. Do not edit `example_backend/`.
2. New code uses our vocabulary (`replay_*`, `knowledge_*`, `provider_settings`), not `eval_*`.
3. No `pydantic-ai`. Pydantic (models, validation) and `pydantic-settings` are fine.
4. Run `ruff` in every phase's done-check.

## 12. Phase 7: a separate knowledge base database, and routing recorded in `knowledge_base_choice` (built)

Added 2026-11-11 after the frontend migration. **All of Phase 7 is built** (see 12.10 and 12.11).

### 12.1 What is wanted

1. **The knowledge base gets its own SQLite instance, `knowledgebase.db`**, separate from `app.db`.
2. **Each agent is given the choices, and the selections are recorded, in a `knowledge_base_choice` table.** When an agent answers, it walks that agent's knowledge base one level at a time:
   - **category** (offered every category that has at least one usable file) -> the agent picks one,
   - **sub category** (offered the chosen category's sub categories) -> the agent picks one,
   - **file** (offered the chosen sub category's files) -> the agent picks one,
   - then it answers with the chosen file as reference material.
     For every level, one row records **what the agent was offered** and **what it selected**. This is the decision tree the Replay Diff tab already knows how to show (the `decision_trace` field, today always empty).

How "the choices and the selections recorded" is read, so it can be corrected:

| Reading  | Meaning                                                                                                                                                                                 | Status                         |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Offered  | At each level the agent sees the list of choices                                                                                                                                        | In scope                       |
| Recorded | One `knowledge_base_choice` row per level, holding the options offered and the selection                                                                                                | In scope                       |
| Fed back | The selections already recorded for this conversation are shown to the agent as a hint when it routes the next question (so a follow-up like "and its logging?" stays in the same area) | **Proposed, needs a yes (K2)** |

### 12.2 Two databases

| File               | Setting                                          | Holds                                                                                                                                    | Migrations                                                                                        |
| ------------------ | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `app.db`           | `DATABASE_PATH`                                  | users, sessions, agents, provider settings, preferences, conversations, messages, chat records, replay runs and results, `stop_requests` | `db/migrations/` (0001-0003 exist; **0004 drops the old `kb_*` tables** after the data has moved) |
| `knowledgebase.db` | `KNOWLEDGE_DB_PATH` (default `knowledgebase.db`) | `kb_categories`, `kb_subcategories`, `kb_documents`, `kb_seeded`, `knowledge_base_choice`                                                | `db/kb_migrations/` (its own numbering from 0001, its own `schema_migrations` table)              |

Both are created and upgraded at startup by the same runner (`db/migrate.py` already takes a directory). Both are SQLite files that persist; neither is ever wiped by `./run.sh`.

**What a second file costs, and how it is handled**

- **No foreign keys across files.** `kb_categories.user_id` and `.agent_id` stay as plain columns (they used to reference `users` and `agents`). The service layer checks the agent against `app.db` before touching the knowledge base, and every query is already scoped by `user_id`. There is no delete-user route today; if one is added it must also delete that user's rows in `knowledgebase.db` (task T7.4 adds the helper).
- **No transaction spans both files.** Routing reads `knowledgebase.db` and the answer is stored in `app.db`, so a choice can be recorded for an answer that then fails or is stopped. That is acceptable and even useful (the choices were really made); the rows are keyed by the request, and a trace is only shown when its answer exists.
- **Two files to back up together.** Documented in the README.
- **Reset.** `./run.sh --reset` and `scripts/reset_db.py --yes` delete both files (a reset that kept the knowledge base would leave rows for users that no longer exist). `--only=knowledge` / `--only=app` resets one.

### 12.3 The `knowledge_base_choice` table (in `knowledgebase.db`)

One row per routing level (so up to three per answer).

```sql
CREATE TABLE knowledge_base_choice (
  choice_id    TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL,
  agent_id     TEXT NOT NULL,
  scope        TEXT NOT NULL CHECK (scope IN ('chat', 'replay')),
  scope_id     TEXT NOT NULL,   -- chat: conversation_id; replay: replay_run_id
  ref          TEXT NOT NULL,   -- chat: the send's request_id; replay: "{slot}:{turn_index}", e.g. "a:2"
  step_number  INTEGER NOT NULL CHECK (step_number BETWEEN 1 AND 3),
  level        TEXT NOT NULL CHECK (level IN ('category', 'subcategory', 'file')),
  model        TEXT,            -- the model that chose (the slot's model in a replay)
  options_json TEXT NOT NULL,   -- what the agent was offered: [{"id": ..., "name": ...}, ...]
  chosen_id    TEXT,            -- NULL unless outcome = 'chosen'
  chosen_name  TEXT,            -- kept so the record stays readable if the item is later renamed or deleted
  reason       TEXT,            -- the agent's one-sentence explanation, if it gave one
  outcome      TEXT NOT NULL CHECK (outcome IN ('chosen', 'none', 'invalid')),
  created_at   TEXT NOT NULL,
  UNIQUE (scope, scope_id, ref, step_number)
);
CREATE INDEX idx_kbc_lookup ON knowledge_base_choice (scope, scope_id, ref);
CREATE INDEX idx_kbc_user_agent ON knowledge_base_choice (user_id, agent_id, created_at);
```

`outcome`: `chosen` (a valid selection), `none` (the agent said nothing is relevant), `invalid` (the agent did not return a usable choice after one retry). A `none` or `invalid` row ends the walk and the answer is given without a reference document.

**Single source of truth.** The assembled `decision_trace` in API responses is built from these rows. `replay_results.decision_trace_json` (today always empty) stays unused and is not written. A chat answer's trace is found through the user message's `request_id` (the server generates one when the client did not send it).

### 12.4 Moving the data that already exists

`app.db` currently holds the `kb_*` tables with real user edits, so the move must not lose data. Startup order:

1. migrate `knowledgebase.db` (creates the tables, empty);
2. **move step** (`db/kb_move.py`): if `app.db` still has `kb_*` tables, `ATTACH` `app.db`, copy `kb_categories`, `kb_subcategories`, `kb_documents`, `kb_seeded` with `INSERT OR IGNORE` (safe to repeat), then **verify the row counts match**; any mismatch or error aborts startup _before_ anything is dropped;
3. migrate `app.db`: **0004 drops the four `kb_*` tables**.

A fresh install skips step 2 (no old tables). SQLite cannot make a copy across two WAL files atomic, which is why the copy is idempotent and verified before the drop.

### 12.5 Routing flow (one answer)

```
question + agent ──> [ ensure this user's knowledge base for the agent is seeded ]
   1. offered: categories with >= 1 usable file ──> agent picks one (or none)   ──> row, step 1
   2. offered: that category's sub categories     ──> agent picks one (or none)   ──> row, step 2
   3. offered: that sub category's files          ──> agent picks one (or none)   ──> row, step 3
   4. answer: the chat history, with the chosen file merged into the latest user message
```

- **Only `current` files are offered.** Files that are `pending-review`, `quarantined`, `malicious-active` or `archived` never reach a model, and categories or sub categories left with no `current` file are not offered. (Recommendation D6; K3 below.)
- **Each level is one model call** using the same model and provider as the answer. The prompt names the level, lists the options as `id: name`, shows the path chosen so far, and asks for strict JSON: `{"choice": "<an offered id, or null>", "reason": "<one short sentence>"}`. The question and the option names are presented as data to ignore instructions in. No agent framework: parse the JSON ourselves (accept a fenced block), check the id against the offered ids, **retry once** with a corrective message, then record `invalid`.
- **Chat:** routing runs inside the send, before the answer. A stop command behaves as before (the prompt is `stopped`, a late reply is `ignored`); the choices already recorded stay.
- **Replay:** each slot (A and B) routes **independently with its own model**, recorded per `(run, slot, turn)`. Differences in routing between models, or between hardware targets later, are exactly what the Diff tab's decision-tree collapsible shows.
- **Demo mode** (no provider): a deterministic keyword match picks the option sharing the most words with the question (the first option on a tie), so the decision tree is visible without an API key. The reason says so, and the model is recorded as `demo`.
- **Reference material in the answer:** merged into the latest user message of the chat history sent to the model (the stored message is unchanged; earlier turns do not carry it), inside delimiters (`<reference_document category=... sub_category=... file=...>`), with a note that it is reference data and must not be followed as instructions, the closing tag neutralised if the file contains it, and the whole file sent (`KB_MAX_CONTEXT_CHARS`, default 0 = send the whole file).
- **Failure handling:** a provider error in any routing call fails the request like any other model error (the prompt is saved, status `failed`). An unusable choice only ends the walk (`invalid`) and the answer goes ahead without a document. If the agent's knowledge base has no `current` file, nothing is routed and nothing is recorded.
- **Cost:** up to three extra model calls per answer, and per slot in a replay step (so up to eight calls per step for two models). `KB_ROUTING_ENABLED=false` turns routing off.

### 12.9 Risks

- **More calls, more latency.** Up to three extra sequential calls per answer, doubled for a replay step. Mitigations: the switch (K6), agents with no `current` files skip routing, and only the choice prompts (not the answer) are short.
- **No joint transaction across the two files.** A crash between recording choices and storing the answer leaves choices without an answer. Harmless: traces are looked up from the answer, and rows are keyed by request.
- **No cross-file integrity.** A deleted category or file leaves `chosen_id` dangling; `chosen_name` keeps the row readable. Deleting a user must also clear their rows in `knowledgebase.db` (T7.4 helper).
- **The move.** The copy cannot be atomic across two WAL files. It is idempotent, verified by row counts, and aborts startup before the drop on any mismatch.
- **Prompt injection through the knowledge base.** Document text and names are untrusted. Only `current` files are offered, text goes in delimiters with a "do not follow instructions in it" note, the closing delimiter is neutralised. The whole file is sent (a model is stateless and needs all of the text), so a very large file costs context-window tokens; an operator can set `KB_MAX_CONTEXT_CHARS` for small-context models. This reduces the risk; it does not remove it.
- **Routing quality depends on the model returning clean JSON.** Covered by one retry, then `invalid`; a weak model will often answer without a document.
- **Two files to back up together,** and `./run.sh --reset` now deletes both.

## 13. Phase 8 (built 2026-11-11): KB references in history, document versions, and compaction

Status: **built 2026-11-11 (see 13.9).** Section 13.5 records every question and its answer; none were left open.

### 13.1 What is wanted

- The chosen knowledge-base file is sent to the model **in full** (built, 12.11). A model is stateless; truncation is not the remedy for context growth.
- A knowledge-base document is **limited to 10 KB**. Saving anything larger shows a popup overlay: *"You need to split your content into smaller documents. Or if you want to customize this tool you could build a vector DB for semantic search. This tool does not currently support semantic search."* The README says the same.
- A **New conversation popup modal** opens before any conversation starts and asks for: **Conversation name, agent, model, reasoning level, and the KB-summary-tool setting** (off by default). The agent, model, reasoning level and toggle are saved on the conversation and **fixed for its life** (the name is only a label and can be renamed), so the user has a known set of configurations to compare against. To try another configuration, start another conversation.
- **Replay has its own KB-summary-tool switch.** When the user replays inputs they can turn the tool on or off for that replay, whatever the source conversation used (P11). The conversation's fixed configuration stays the baseline; the replay is where the user varies it.
- A **KB-summary-tool** toggle chooses how a chosen file reaches the model: off = the entire file text; on = a model-written summary of it (13.3 item 3).
- File text must not be copied into storage once per turn. History records a **reference** (document id + version), and the text is read from the version row when the history is built.
- A user can press a **Compact** button. A model writes a summary; the summary becomes the first message (`compacted_summary`) of a **new conversation**, so there is a clear boundary between conversations. This is a teaching tool: the user watches how a stateless model behaves when it is handed only a summary.

### 13.2 What the current schema supports

- `messages` has `role`, `status`, `request_id`, `sequence_number`, but **no `message_type`**. A summary or a reference row cannot be told apart from a normal turn. Needs an additive migration (never edit an applied one).
- `knowledge_base_choice` records the path (names and ids) but **not which version of the text was sent**. Editing a file afterwards makes the record unable to say what the model saw.
- Documents have no version history: an edit overwrites `content`. The upload limit is 200 KB today; the decided limit is 10 KB.
- The model's history is every non-ignored message in order; there is no conversation-to-conversation link.

### 13.3 Design

1. **Versioned documents** (`knowledgebase.db`, new migration): `kb_document_versions(version_id uuid PK, document_id, version_number, content_hash, content, created_at)`. An edit creates a new version only when the hash changes. `knowledge_base_choice` gains `document_version_id`. Text exists once per version, never per turn. No KB-wide counter (P4).
2. **`message_type`** on `messages` (`chat` default, `kb_reference`, `kb_summary_tool`, `compacted_summary`; additive migration, existing rows stay `chat`). A `kb_reference` row stores **no text**: it holds the `document_version_id` (and the path names for display). Whoever builds model history expands it from the version row.
3. **KB-summary-tool toggle** (decision P3), set per conversation in the New conversation modal (Q1, item 8) and fixed afterwards.
   - **Off (default): the entire file is sent.** The choice writes a `kb_reference` row (version id, no text). The history builder expands `kb_reference` rows into the framed `<reference_document>` block at their turn (Q8), which is affordable because a document is at most 10 KB.
   - **On: an independent model call summarises the file for this conversation.** The prompt is: *"Considering the current conversation {conversation_history_wrapper}. Summarize the relevant information about this {KB_content} such that the useful information is listed in less than 1000 words."* The reply is stored in the message history as a row of type `kb_summary_tool` (with the `document_version_id`), and **that summary is sent in place of the file text**. The 1000-word limit is an instruction to the model, not enforced by the server. The call uses the conversation's current model configuration, runs after routing and before the answer, and honours stop (a stopped summary is discarded like a stopped answer). If the summary call fails, the request fails, as a provider error does elsewhere.
   - **History builder** is one function used by chat and replay. It maps rows by type: `chat` as is, `kb_reference` to the framed file text, `kb_summary_tool` to a framed block labelled as a summary of the named file, `compacted_summary` as the first turn.
8. **Conversation configuration** (decision P10). A conversation row holds `name`, `agent_id`, `model`, `reasoning_level`, `kb_summary_tool` (0/1), all `NOT NULL` for new conversations. **Only `name` can change** (a free label, Q11); agent, model, reasoning level and the toggle are **immutable**: `PATCH /conversations/{id}` accepts `name` alone and refuses any other field with `409`. The modal is the only way to create one: `POST /conversations` takes the five fields; the chat page shows the configuration read-only in its header; the send route no longer accepts `model` or `agent_id` from the client (they come from the conversation, so a message can never run with a different configuration than the one being compared). Older conversations and the sample conversation are backfilled from their last message (agent, model) with reasoning `none`, summary tool off, and a generated name; a conversation with no messages gets the user's saved preferences. `reasoning_level` is a new concept: nothing in the backend or frontend carries it today; it follows OpenAI's `reasoning_effort` options (Q10), default `default`.
9. **Replay and the toggle** (decision P11). The Replay page has a KB-summary-tool on/off control, initially set from the source conversation's value and changeable until the replay starts (a started run keeps its value, like its models). It applies to **both slots and every step of that run**, so Model A and Model B are compared under the same setting. `replay_runs` gets `kb_summary_tool`. A replay step is a fresh answer to the user's prompt with that slot's own earlier replay results as history (as built), so with the switch on **each slot makes its own summary call with its own model**; the summary text is saved on the replay result (`replay_results.kb_summary`, new nullable column; replay does not write `messages` rows) and shown in the Diff next to the decision tree, so the user can see what each model was handed. A stopped or discarded step leaves no summary, like no answer. With the switch off the whole file is sent. Replaying a conversation that has a `compacted_summary` starts from the summary (P8, Q7).
4. **Compaction**: `POST /conversations/{id}/compact` has a model write the summary from the conversation (reference text included, P7), creates a **new conversation** whose first message is the `compacted_summary` (with `source_conversation_id` pointing back) and which **copies the whole fixed configuration** (agent, model, reasoning level, toggle) with the name `<name> (summary)`, and returns it. The old conversation is untouched. The summary cannot be edited by the user (P5).
5. **Replay** covers a conversation up to its summary. A conversation that starts with a summary replays from that summary: the summary is the first turn of that history (P8).
6. **Deleting a document version** (P2): deletion wins. The version row is removed. Rows that referenced it (`knowledge_base_choice`, `kb_reference` messages) stay readable by names and are **flagged `kb_version_deleted`** in responses, so Replay chat histories show that the version used is gone. The delete call first reports how many conversations used the version and asks the user whether to delete those conversation records too (13.5 Q4 for the API shape). Where a kept conversation's reference can no longer be expanded, the history builder sends a one-line placeholder naming the deleted file, never text.
7. **10 KB limit** is enforced when a document is created or edited, in UTF-8 bytes (Q2). The API rejects it with `422`, code `kb_document_too_large`; the frontend shows the popup text from 13.1. It is not enforced by truncation at send time. `KB_MAX_CONTEXT_CHARS` is no longer needed as a send-time cap.

| Q14 | One replay switch for both slots, or one per slot? | **Decided: one switch for the whole run.** Both slots follow it, so the only differences between A and B are the model (and hardware) under study. To compare summary against whole file, run two replays, one on and one off; the Diff shows which setting each run used. |
| Q15 | In a replay, which model writes each summary? | **Decided (recommendation adopted):** in a replay each slot's own model writes its summary (it is what that slot would do in a real conversation); the summary text is saved on the replay result and shown in the Diff. |

### 13.7 Risks

- Making the configuration fixed removes today's ability to switch agent or model mid-conversation on the chat page; that is the intent (a clean comparison), but existing habits and the current tests that change model between messages need to change.
- Duplicate names are allowed (Q11), so the conversation list and the comparison views must show something beyond the name (agent, model, reasoning level, date, and a short id) to tell two chats apart.
- A summary loses detail the user later wants. The old conversation is kept untouched, and the new one links back to it.
- A summary written by a weak model can be wrong and the user cannot edit it (P5, by design for v0). The link to the source conversation is the check.
- The 10 KB limit makes some real documents unusable until split; the UI must say why, and say that semantic search is not part of this tool.
- Reference rows plus version deletion create dangling references by design (P2); the flag and the placeholder keep that visible and safe.
- Backfilling versions touches every document once; idempotent and verified by count, like the earlier move (12.4).
- With the toggle off, a long conversation can re-send every chosen file (up to 10 KB each) each turn (Q8); compaction is the remedy. With it on, each file choice costs an extra model call and depends on that model's summary; a poor summary stays visible because the `kb_summary_tool` row is stored.
- A replay switch means two runs of the same prompts can differ only by the summary setting; the Diff must show which setting each run used, or comparisons mislead. Each slot's summary is its own model's output, so a summary difference can look like a model difference; the Diff shows the summary text to make that visible.

### 13.9 As built (2026-11-11)

All of 13.6 is done: **335 backend tests** (`ruff` clean), **177 frontend tests**, **13 live tests** against a real backend, and
`scripts/smoke.sh` extended (settings fixed, rename, summary tool, compact, replay summaries) and run against a real server.

Decisions made while building (none contradict 13.4):

- **Internal rows use `role = 'user'`** (the `messages.role` CHECK cannot change without rebuilding the table) and are told
  apart by `message_type`; every query that means "the user's prompts" filters on `message_type = 'chat'`. They share the prompt's
  `request_id`, are hidden from the visible list, and are deleted when their turn fails, is stopped or is rewound.
- **`kb_reference.content` holds the path as JSON, never the file's text.** The text is read from `kb_document_versions` when
  the history is built (`services/history_service.py`, used by chat and replay), so editing a file later does not change what an
  earlier turn is sent: each turn is re-sent with the exact version it used (Q8).
- **`KB_MAX_CONTEXT_CHARS` was removed**; the size limit is enforced when a file is saved (`KB_MAX_DOCUMENT_BYTES`, 10240).
- **Replay "delete the records too"** covers conversations and replay runs, and the 409 reports both counts
  (`{conversations, replays}`). Deleting a category, a sub category or "Restore defaults" asks the same question as deleting a
  file (the versions go either way).
- **Reasoning level** applies to answers, KB summaries and Compact, not to the routing calls. A `400` from the provider shows the
  provider's own reason (`API returned HTTP 400: ...`); there is no retry without the field.
- **Replay slot B** starts as the first model that is not slot A's (A starts as the conversation's model).
- **Older data**: migration 0006 fills agent and model from a conversation's latest answer, else the saved preferences; a
  conversation with neither gets the user's first model the first time it is opened (then it is fixed). `knowledge base` files
  get their version 1 from `db/kb_versions.py` at startup (idempotent, verified).
- **Frontend**: the settings chips are read-only on the chat page; the popup is shared (`shared/modal-ui.js`); the chat page no
  longer changes the remembered agent or model, the popup does (it starts from the last choice).

Not built (not asked for): a list of conversations (the page works on "current"; Compact and "New chat" make the new one current),
navigation from a summary conversation to its source, saved configuration templates.
